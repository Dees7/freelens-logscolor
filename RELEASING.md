# Релиз ветки `v1` (Freelens 1.x, Lens 6.x)

Поток релизов у веток свой у каждой: мажор пакета равен мажору хоста, так что в этой ветке
версии всегда `1.x.y`, а теги — `v1.x.y`. Ветку `v2` релиз отсюда не трогает, и наоборот.

Релизов пока не было: первый будет `v1.0.0`.

## Порядок

1. Проверить, что всё сходится:

   ```sh
   npm run check    # типы, тесты, сборка, smoke на собранном бандле
   ```

   Плюс живая проверка: `npm run build`, Cmd+R в приложении, открыть логи пода и убедиться,
   что цвет на месте, а поиск и дозагрузка работают. Smoke знает только форму хоста; того, что
   настоящий вьювер правильно покажет ANSI, он не проверяет. Если под рукой есть и Lens 6.x —
   проверить и там: манифест обещает обоих.

2. Поднять версию. Мажор — только вслед за мажором Freelens:

   ```sh
   npm version patch    # или minor
   ```

   Команда сама создаёт коммит и тег `v1.x.y`.

3. Собрать артефакт:

   ```sh
   npm run pack         # прогоняет check и кладёт freelens-logscolor-1.x.y.tgz
   ```

4. Отправить и выложить:

   ```sh
   git push origin v1 --follow-tags
   gh release create v1.x.y freelens-logscolor-1.x.y.tgz \
     --title "v1.x.y — Freelens 1.x / Lens 6.x" \
     --notes "…"
   ```

   В заголовке релиза хост указывается всегда: в списке релизов рядом будут стоять `v1.x.y` и
   `v2.x.y`, и по одному номеру непонятно, что из них ставить.

## Что не забыть

- Изменение логики раскраски, которое касается обеих веток, переносится в `v2` черри-пиком, а
  не слиянием: ветки расходятся сборкой, манифестом и константой `FAINT`.
- Релиз в `v2` после этого — отдельный, со своим номером. Одинаковых номеров у веток не бывает,
  поэтому «та же версия для v2» — это не `v2.<те же цифры>`, а следующий патч ветки `v2`.
- В npm пакет не публикуется: расширения Freelens ставятся из `.tgz` или из каталога.
