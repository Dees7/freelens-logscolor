# Релиз ветки `v2` (Freelens 2.x)

Поток релизов у веток свой у каждой: мажор пакета равен мажору хоста, так что в этой ветке
версии всегда `2.x.y`, а теги — `v2.x.y`. Ветку `v1` релиз отсюда не трогает, и наоборот.

Релизов пока не было: первый будет `v2.0.0`.

## Порядок

1. Проверить, что всё сходится:

   ```sh
   npm run check    # типы (нужен ../freelens), тесты, сборка
   ```

   Плюс живая проверка: `npm run build`, Cmd+R в Freelens, открыть логи пода и убедиться, что
   цвет на месте, а поиск и дозагрузка работают. Автотесты стерегут только неизменность текста
   — того, что хост правильно показывает ANSI, они не знают.

2. Поднять версию. Мажор — только вслед за мажором Freelens:

   ```sh
   npm version patch    # или minor
   ```

   Команда сама создаёт коммит и тег `v2.x.y`.

3. Собрать артефакт:

   ```sh
   npm run pack         # прогоняет check и кладёт freelens-logscolor-2.x.y.tgz
   ```

4. Отправить и выложить:

   ```sh
   git push origin v2 --follow-tags
   gh release create v2.x.y freelens-logscolor-2.x.y.tgz \
     --title "v2.x.y — Freelens 2.x" \
     --notes "…"
   ```

   В заголовке релиза хост указывается всегда: в списке релизов рядом будут стоять `v1.x.y` и
   `v2.x.y`, и по одному номеру непонятно, что из них ставить.

## Что не забыть

- Изменение логики раскраски, которое касается обеих веток, переносится в `v1` черри-пиком, а
  не слиянием: ветки расходятся сборкой, манифестом и константой `FAINT`.
- Релиз в `v1` после этого — отдельный, со своим номером. Одинаковых номеров у веток не бывает,
  поэтому «та же версия для v1» — это не `v1.<те же цифры>`, а следующий патч ветки `v1`.
- В npm пакет не публикуется: расширения Freelens ставятся из `.tgz` или из каталога.
